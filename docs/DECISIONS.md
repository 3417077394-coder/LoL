## DEC-0001：文档即代码

日期：2026-08-14  
状态：Accepted

决定：

- 根 `README.md` 记录当前阶段和文档入口。
- `PROJECT_DESIGN.md`、`BASELINE_DESIGN.md` 和
  `DATA_DESIGN.md` 记录当前设计。
- `EXPERIMENT_LOG.md` 记录历史运行。
- 本文件记录重要决定的原因。
- 聊天记录不作为项目事实来源。

原因：项目设计已经跨越多个对话，仅依赖聊天会造成上下文丢失和重复解释。

影响：任何改变行为或实验解释的代码修改，都必须同步修改对应文档。

## DEC-0002：冻结 baseline-test-v1

日期：2026-08-14  
状态：Accepted

决定：把当前 50 条清洗后阵容输入定义为 baseline-test-v1，禁止进入
few-shot、SFT 和偏好训练。

原因：后续提升必须在未见测试数据上衡量，否则无法区分泛化和记忆。

限制：50 条规模较小且原始创作 ruleset 未知；未来可建立 v2，但不能静默替换 v1。

## DEC-0003：Baseline 使用 greedy decoding

日期：2026-08-14  
状态：Accepted

决定：Baseline v1 使用 `do_sample=false`，不传入 temperature/top_p。

原因：降低重复实验的随机噪声，使 zero-shot、few-shot 和 SFT 的差异更容易
归因于模型或 Prompt。

限制：该设置不测量模型输出分布和采样稳定性；如需研究采样，应建立独立
实验而不是改变 Baseline v1。

## DEC-0004：Judge 关联和错误处理

日期：2026-08-14  
状态：Accepted

决定：

- Judge 通过 `sample_id` 与 canonical 测试集重新关联。
- 推理记录同时保存 `input_scenario` 和 `input_prompt`。
- API、解析和关联失败写入 `evaluation_error`。
- 失败不伪造成 0 分，也不进入平均值。

原因：系统故障不是模型语义能力，混入 0 分会系统性压低结果；没有真实阵容
输入的 Judge 分数无效。

## DEC-0005：三层评估

日期：2026-08-14  
状态：Accepted

决定：

1. 程序全量检查 JSON、Schema 和硬约束。
2. LLM Judge 全量或大规模检查事实与因果。
3. 人工分层抽查校准 Judge 并发现隐藏错误。

原因：格式合法不能证明语义正确，而 LLM Judge 也不是绝对真值。

## DEC-0006：人工审核协议

日期：2026-08-21  
状态：Accepted

决定：

- 按 Evaluation Rubric v1.0 从正式输出中分层抽取 12 条。
- 至少两名领域审核者独立盲审，逐检查项评分并引用模型原文证据。
- 正式审核前使用 3 条非冻结测试集练习输出校准，不把练习结果计入实验。
- 报告线性加权 Cohen's kappa 和平均绝对分差；维度差异达到 2 分时复核。
- kappa 小于 0.60 或平均绝对分差大于 1.0 的维度标记为一致性不足。
- “存在另一种合理打法”不自动算错；明确事实错误、输入不支持的断言和内部矛盾必须可举证。

限制：当前 `human_review.py` 仍是旧的双分数结构，只有完成 Rubric v1.0 适配后
才能用于正式 EXP-0001。

## DEC-0007：正式实验产物不可静默覆盖

## DEC-0010：能力与错误共同驱动数据采集

日期：2026-08-15  
状态：Accepted

决定：

- 使用版本化的阵容分析能力 ID 标注 baseline 错误、few-shot 示例和 SFT 数据。
- 初始覆盖由任务的能力分类体系给出，正式采集优先级由修正后的 baseline 错误分布校准。
- 教学视频、比赛分析、文章和转写只作为来源材料；不能仅因其与 LoL 相关就直接训练。
- 冻结测试集的能力与错误记录保存在 sidecar，通过 `sample_id` 关联，测试集本体不改动。
- Pilot 使用重叠能力标签检查学习信号；正式 baseline 错误分布出现前不设逐能力精确配额。

原因：只按内容来源批量采集会混入大量与静态 BP 任务无关、缺乏可验证答案或依赖
比赛动态状态的文本；只按预设知识目录采集又可能忽略模型实际失败。两条证据结合才
能让数据投入与可测能力提升建立联系。

影响：后续采集、合成、审核和实验报告应引用当前能力目录；能力 ID 的语义变化需要
发布新版本，不能静默修改历史标签。五个一级维度与知识库边界由 DEC-0011 进一步明确。

## DEC-0011：版本事实外置与双层 Baseline

日期：2026-08-15  
状态：Accepted

决定：

- 阵容分析使用五个一级评估维度组织报告，19 个细项保留为二级诊断标签。
- 当前正式 baseline 定义为 closed-book / model-only baseline，不接外部知识库。
- 英雄技能、定位和游戏规则等版本化事实由未来外部知识库维护；SFT 主要训练如何依据
  给定事实完成交互、整体阵容和制胜条件推演。
- 生产知识库可以动态更新，但实验必须固定 `ruleset_id`、Data Dragon 构建、知识
  截止日、知识快照和检索逻辑。
- 知识库完成后，新增 base+fixed-KB baseline；不得覆盖当前 closed-book 实验。
- SFT 主要比较 base+KB 与 SFT+同一 KB，并额外检查检索完整性、版本一致性和知识忠实度。
- 在正式 baseline 错误分布出现前，SFT pilot 只保留 200～500 条总体规模范围，不设置
  逐能力精确配额。

原因：版本事实会变化，依靠参数记忆会迅速过时；同时，过细的一级指标和无依据的
精确样本配额会增加执行负担。把事实获取与推理能力分开，既能保持系统更新能力，也
能通过固定快照保证实验可复现。

影响：当前 baseline 的事实错误被解释为知识缺口诊断；真正衡量 SFT 推理增益时，应
控制知识上下文一致。知识库 Schema、数据、检索实现和 fixed-KB 实验均尚未完成。

## DEC-0012：采用五维输出评分 Rubric v1.0

日期：2026-08-21  
状态：Accepted

决定：

- E1～E5 评判的是给定输入下的一条阵容分析任务输出，不把文风流畅等同于模型能力。
- 每个一级维度包含 5 个检查项，每项取 0、0.5、1 或 NA；按可评项归一化为 0～5 分。
- E1 是输入与输出质量门槛，E2 是当前知识缺口诊断，E3～E5 是 SFT 重点推理能力。
- 每个扣分和 NA 都必须保留模型原文证据、解释、二级标签、严重度和置信度。
- 严重机制幻觉、缺少团队聚合、通用战术口号和因果矛盾使用 Rubric 中的封顶规则。
- E1 单独报告；辅助语义综合分采用 E2 20%、E3 25%、E4 25%、E5 30%，同时必须
  展示各维度和检查项分布。
- 评估系统故障写入 `evaluation_error`，不伪造成模型 0 分；语义不可评率单独报告。
- Rubric 同时用于 baseline、教师候选和专家任务答案，但不直接用于原始视频转写或文章。

原因：五个一级维度只有具体、带证据的检查项才能降低审核随意性；分开格式、知识、
交互、聚合和制胜条件，才能把问题分别路由到程序、知识库和 SFT。

影响：正式 EXP-0001 前必须实现五维评估 Schema，并适配 Judge、人工审核和汇总代码。
当前旧的 factual/consistency 两分结构仍可追溯，但不能冒充 Rubric v1.0 结果。

## DEC-0014：Champion Knowledge Card 分层 Schema 与精确查询

日期：2026-08-21  
状态：Partially superseded by DEC-0017

决定：

- 英雄知识卡分为身份与来源事实、规范化机制、战术属性、出处与审核四层；派生内容必须
  保留来源事实 ID 和生成方式。
- v1 以稳定英雄 ID、指定 ruleset 和 locale 做确定性精确查询，不把向量检索设为必需环节。
- 多形态英雄通过同一技能槽的多个 `form_id` 记录表达，不为每个形态复制整张英雄卡。
- 英雄两两克制、十人阵容协同、制胜条件、胜率和出装结论不写入英雄事实卡，由模型基于
  当前阵容和检索事实推导。
- 只有 `approved` 状态且通过 Schema、来源、版本和人工事实审核的卡片可进入正式固定快照。
- 现有 `data/reference/champions_zh.snapshot.json` 是 16.15.1 的迁移参考，不是
  Data Dragon 16.16.1 已审核知识快照。

原因：把可变事实、人工规范化标签和阵容级推理结论混在一起，会让来源追溯、版本更新和
能力归因失效；确定性精确查询更适合已知十名英雄的封闭输入，也便于复现实验。

影响：机器契约位于 `schemas/champion_knowledge_card_v1.schema.json`，详细规则见
`docs/KNOWLEDGE_BASE_DESIGN.md`。本决定只冻结 Schema v1 的能力边界；版本字段已由
DEC-0015 在正式采集前修订。Data Dragon 16.16.1 真实卡片、来源采集、语义校验器、
固定快照和上下文生成器仍待实现。

  `ruleset_id`、`ddragon_version`、`public_patch_alias`、`as_of` 和
  `region_scope`。
- 现有 16.15.1 参考快照继续只作迁移参考；正式 16.16.1 知识数据和上下文生成器尚未实现。

## DEC-0017：全英雄来源约束知识快照取代逐卡人工战术审核

## DEC-0019：正式实验前改用紧凑的阵容关键机制上下文

日期：2026-08-24

实现约束：

- 完整 Champion Knowledge Card 和 `full` 上下文保持只读；紧凑内容是派生视图
  `compact-mechanics-v1`，可由来源卡片离线重建。
- 只输出客户端直接标记的伤害/控制/机制索引和来源卡的 `summary_zh`；关键词仅用于
  技能排序，不让 LLM 补写或改写英雄事实。
- 普通英雄最多保留 4 个关键技能，复杂形态英雄最多保留 5 个，避免为追求 token
  数而漏掉波比推墙、锤石灯笼、厄斐琉斯武器队列等关键机制。
- 实验必须记录 context view、派生清单哈希和最终上下文哈希；Judge 按记录重建同一视图。

实现结果：173 份紧凑上下文已生成，全库字符数为完整视图的 64.26%；39 个本地测试
通过。`DEV-KB-0003` 实测 fixed-KB 平均输入较完整视图减少 28.36%、延迟减少 14.93%，
JSON/Schema 从 8/9 恢复为 9/9；但隐藏 A/B 只胜 2/9，低于 `DEV-KB-0002` 的 3/9。
因此紧凑 v1 不提升为正式 Prompt，也不扩到正式 50 条。压缩只能解决成本和部分格式
问题，不能替代模型的实体绑定与知识忠实使用能力。

证据：`DEV-KB-0001` 与 `DEV-KB-0002` 中，fixed-KB 的隐藏条件单审核者偏好分别为
2/9、3/9，两轮各有 1 条 JSON 尾逗号失败。第二轮显式实体映射后平均输入仍增加
5,267.556 tokens、平均延迟增加 7.308 秒。随后 `gpt-5.6-sol` E1～E5 Judge 对
`DEV-KB-0002` 判 closed-book 6 胜、fixed-KB 3 胜，平均语义分 1.894 对 1.699；
fixed-KB 的知识忠实度均值仅 1.167/5，并出现更多跨实体和无依据机制断言。

限制：证据仍只来自 9 条开发样本；API 结果只有一个 LLM Judge，尚未经过双人专家
盲审校准。因此这里只拒绝当前完整十卡 Prompt 模板，不否定知识库本身；紧凑模板仍需
在同一开发样本上复验，方向转正后才能进入正式评估。
