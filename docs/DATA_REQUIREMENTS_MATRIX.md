# 数据需求矩阵

状态：Data Requirements Matrix v1.1（试运行）  
最后更新：2026-08-21

## 1. 总原则

数据需求由两条证据共同决定：

```text
能力体系（任务需要什么）
            +
Baseline 错误（当前模型缺什么）
            ↓
知识库建设 / SFT 数据建设 / 程序修正
```

不是所有 LoL 内容都应进入 SFT，也不是所有模型错误都应通过微调解决：

- 版本化英雄与规则事实 → 优先进入知识库。
- 事实正确但不会组合推理 → 通过 SFT 改善。
- JSON、字段和实体硬错误 → 优先程序约束，必要时少量训练。
- 原始视频、解说和文章 → 只是来源材料，不能直接作为训练答案。

## 2. 目标系统中的数据流

```text
版本化 FACT 知识
      ↓ 检索
阵容 + knowledge_context
      ↓
INTERACTION / FULL / CF / REPAIR
      ↓ 审核
SFT：学习依据知识进行阵容推演
```

生产知识库可以随版本更新；任何 baseline、few-shot 或 SFT 实验必须绑定固定的
`ruleset_id`、`ddragon_version`、`ruleset_as_of` 与 `knowledge_snapshot_id`，
否则不同时间的结果不可比较。

## 3. 数据单元

| 代码 | 数据单元 | 主要用途 | 默认去向 |
|---|---|---|---|
| `FACT` | 原子、可核验、带版本的英雄或游戏规则 | 提供机制事实和审核依据 | 知识库，不直接作为 SFT 答案 |
| `INTERACTION` | 两至三个英雄/机制的对线、协同或克制关系 | 训练短链条件推理 | 审核后进入 SFT |
| `FULL` | 完整十英雄阵容的结构化分析 | 训练整体阵容与制胜条件 | 审核后进入 SFT |
| `CF` | 只替换一个英雄、换边或改变一个前提的反事实对 | 训练因果敏感性、减少模板化 | 成对审核后进入 SFT |
| `REPAIR` | 错误定位和修正版 | 定向修复事实使用、因果或格式问题 | 只训练修正版或修订任务 |
| `SOURCE` | 获授权的视频片段、转写、文章或解说 | 抽取事实和推理候选 | 不直接训练 |

## 4. SFT Pilot 覆盖矩阵

首轮仍以 **200～500 条高质量样本**作为规模范围，但在修正后的 baseline 完成错误
标注前，不设看似精确的逐类条数。覆盖分为四种规则：

- **全部通过**：每条正式样本都必须满足。
- **核心覆盖**：pilot 必须覆盖多种阵容原型与难度，是主要数据投入。
- **针对补充**：由 baseline 错误率、严重度和测试覆盖决定是否扩充。
- **知识库优先**：事实进入知识库，SFT 只训练检索后如何使用事实。

| 一级维度 | 二级标签 | 数据策略 | 推荐单元 | Pilot 验收方式 |
|---|---|---|---|---|
| `E1` 输入与输出契约 | `B01`, `B02`, `Q03` | 全部通过；不单独追求大量格式样本 | 所有单元、少量 `REPAIR` | 所有 approved 样本实体一致并通过 Schema |
| `E2` 机制事实准确性 | `K01`～`K03`, `Q01` | 知识库优先；按 closed-book 错误建立事实缺口清单 | `FACT`；含知识上下文的 `INTERACTION`/`FULL` | 事实可追溯、版本一致；回答忠实使用给定知识 |
| `E3` 阵容交互推理 | `R01`～`R03` | 核心覆盖 | `INTERACTION`, `CF`, `FULL` | 覆盖对线、协同、克制与反制，结论包含条件 |
| `E4` 阵容整体推演 | `C01`～`C02`, `T01`～`T02` | 核心覆盖 | `FULL`, `CF` | 覆盖多种阵容原型、结构短板、强弱期和资源转换 |
| `E5` 制胜条件与因果 | `P01`～`P04`, `Q02` | 核心覆盖并按错误针对补充 | `FULL`, `CF`, `REPAIR` | 双方路径有区分、可执行、具体且形成因果闭环 |

一条高质量 `FULL` 样本可以同时覆盖 `E3`～`E5` 和多个二级标签。二级标签用于
检查学习信号是否缺失，不是互斥配额。任务答案的逐项审核使用
[Evaluation Rubric v1.0](EVALUATION_RUBRIC.md)；原始来源材料不直接套用该评分。

## 5. 知识库数据需求

机器可读字段、分层边界、审核状态和查询契约见
[知识库设计](KNOWLEDGE_BASE_DESIGN.md)。

知识库至少应支持：

| 数据 | 最小字段 |
|---|---|
| 英雄身份与别名 | 稳定英雄 ID、中英文官方名称、别名、资源与客户端角色 |
| 关键技能事实 | 技能 ID、结构化描述、触发/目标/限制、来源 |
| 机制提示 | 来源中明确标记的伤害类型、状态词、近远程、条件与复杂形态描述 |
| 游戏规则 | 与线权、视野、地形、中立资源和节奏直接相关的规则 |
| 版本记录 | 生效/失效 Data Dragon 构建、公开补丁别名、知识截止日、来源、抓取时间、审核状态 |

结构化英雄查询应优先使用稳定 ID 和指定版本的精确查找，而不是只依赖向量相似度。
较长的补丁说明或来源文章可以使用语义检索，但检索结果仍需保留来源与版本。

主观结论不应写成知识库事实，例如“某阵容必胜”“某英雄必然克制另一英雄”。知识库
提供可核验依据，克制、协同和制胜条件由模型结合当前十名英雄推导。

## 6. 来源与用途

| 来源 | 适合提取 | 不能直接做什么 | 入库门槛 |
|---|---|---|---|
| 官方英雄资料、补丁和规则资料 | `FACT`、版本变更 | 自动成为完整战术答案 | 保存出处、版本、时间和使用依据 |
| 获授权的教学视频/文章 | 局部 `INTERACTION`、术语表达、事实候选 | 原样 transcript 进入 SFT | 片段抽取、去口语噪声、事实核验、授权记录 |
| 获授权的赛前 BP 分析 | `FULL`、阵容结构和推理链候选 | 把队伍/选手特有结论直接泛化 | 去除赛事特有前提、复核版本与可迁移因果 |
| 比赛中实时解说 | 状态无关的机制片段 | 作为静态 BP 完整答案 | 排除经济、装备和已发生结果等动态泄漏 |
| 领域专家原创标注 | `INTERACTION`, `FULL`, `CF` 和审核 | 单人意见成为唯一战术真值 | 使用 rubric；事实需证据，策略允许合理多解 |
| 教师模型合成 | 扩展 `FULL`, `CF`, `REPAIR` 候选 | 自动成为黄金答案 | Schema、事实、因果、去重和防泄漏全部通过 |
| 冻结测试集及其输出 | 误差统计与需求定位 | few-shot、SFT 或偏好训练 | 永不训练；只通过 `sample_id` 做旁路标注 |

没有明确使用依据的外部材料只能用于人工研究和选题启发，不能默认进入可训练或可发布
的数据集。

## 7. 候选样本最小元数据

未来面向知识库的 SFT 候选至少记录：

```json
{
  "sample_id": "sft-pilot-v1-000001",
  "dataset_version": "sft-pilot-v1",
  "unit_type": "FULL",
  "primary_dimension_id": "E5",
  "capability_ids": ["R02", "C01", "P01", "P04", "Q02"],
  "ruleset_id": "lol-pc-ddragon-16.16.1-asof-2026-08-21",
  "ddragon_version": "16.16.1",
  "public_patch_alias": "26.16",
  "ruleset_as_of": "2026-08-21",
  "knowledge_snapshot_id": "kb-ddragon-16.16.1-zh_CN-v1",
  "retrieved_fact_ids": ["fact-id-1", "fact-id-2"],
  "source_type": "expert | official | licensed_creator | synthetic_reviewed",
  "source_ref": "可追溯引用或内部来源 ID",
  "usage_basis": "授权/许可/自有/待确认",
  "review_status": "generated | schema_valid | fact_checked | reviewed | approved",
  "reviewer_ids": [],
  "created_at": "ISO-8601"
}
```

`usage_basis=待确认` 的候选不得进入 `approved`。能力标签必须由答案中实际存在的
学习信号支持，不能为满足覆盖而虚标。

## 8. Baseline 如何反推建设优先级

当前 closed-book baseline 完成后：

1. 不修改 `data/eval/baseline-test-v1.jsonl`。
2. 在 sidecar 中按 `sample_id` 标记二级错误标签、严重度和原文证据。
3. `E2` 错误形成知识库事实缺口清单，不直接等同于 SFT 配额。
4. `E3`～`E5` 中“事实正确但推理失败”的错误决定 SFT 补数据方向。
5. 同时报告每个维度的测试覆盖；没有覆盖不能解释为模型已经掌握。
6. 知识库建成后，用固定快照运行 base+KB，再与 SFT+同一 KB 比较。

建议的未来 sidecar 路径仍为
`data/eval/baseline-test-v1.capabilities.jsonl`。当前尚无修正后的正式 baseline，
因此不创建伪造标注。

## 9. 首轮执行顺序

1. 完成当前 closed-book baseline，获得原始知识与推理错误分布。
2. 用少量独立专家样本试标五个一级维度和二级错误标签。
3. 已完成：按 Champion Knowledge Card v2 建立可追溯的 Data Dragon 16.16.1 全英雄知识快照。
4. 运行 base+固定知识库 baseline，分离“缺知识”和“不会使用知识”。
5. 构建约 50 条专家种子，重点覆盖 `E3`～`E5`，输入包含固定知识上下文。
6. 扩展到 200 条时先做小规模训练检查；质量稳定后再扩到 500 条。
7. 最终比较 base+KB 与 SFT+同一 KB，决定是否继续扩量。

在步骤 1～4 完成前，不应根据来源易得程度大规模采集 SFT 数据。
