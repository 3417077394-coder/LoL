# 静态阵容分析输出契约

状态：Lineup Analysis Output Schema v2（Accepted，代码迁移待完成）  
最后更新：2026-08-26

## 1. 目的与任务边界

本契约定义第一阶段模型应该输出什么。输入是 BP 结束后的双方十名英雄及其位置，输出是
双方静态阵容分析，不是实时比赛指挥，也不要求逐路操作教学。

第一阶段只回答四个问题：

1. 蓝方和红方分别是什么阵容；
2. 双方最关键的 3～5 个协同、克制或局部对位的全局影响是什么；
3. 双方分别在什么强势阶段与交战条件下更容易发挥；
4. 双方怎样才能兑现阵容优势，以及主要失败风险是什么。

本阶段不要求逐路控线、换血细节、刷野路线、Gank 时间、出装、符文、技能加点，或基于
实时金币、装备、资源和选手状态的建议。局部对位只有在显著影响线权、支援、野区或资源
获取时，才作为 `对位影响全局` 写入关键交互。

机器可读契约：
[`lineup_analysis_output_v2.schema.json`](../schemas/lineup_analysis_output_v2.schema.json)。  
说明性示例：
[`lineup_analysis_output_v2.example.json`](../schemas/examples/lineup_analysis_output_v2.example.json)。

示例仅用于解释和 Schema 回归测试，不是专家黄金答案，不得进入冻结测试、few-shot 或
SFT 数据。

## 2. 顶层结构

| 字段 | 回答的问题 | 主要评估维度 |
|---|---|---|
| `team_profiles` | 双方是什么阵容，有什么优势与短板 | E2、E4 |
| `decisive_interactions` | 哪些协同、克制或对位影响最关键 | E2、E3 |
| `comparative_outlook` | 强势期、团战结构、交战条件和地图影响 | E3、E4 |
| `win_conditions` | 双方如何执行、需要什么条件、怎样会失败 | E5 |
| `risks_and_uncertainties` | 哪些结论因版本、位置或输入不足需要保留 | E1、E2 |

顶层固定携带 `schema_version: lineup-analysis-output-v2`。所有对象拒绝未声明字段，所有
要求填写的文本必须是非空字符串。

## 3. 阵容类型：受控标签与自由总结并存

`archetype_tags` 每方选择最相关的 1～3 个标签，不强迫输出唯一主类型：

- `强开团`
- `反开保护`
- `前后排正面团`
- `后排突进`
- `消耗推进`
- `抓单`
- `小规模作战`
- `保核`
- `边线分推`

标签用于统计、分层和稳定生成；`composition_summary` 用自由文本解释混合形态、主要
执行链和结构依赖。`全短手`、`双刺客`、`伤害类型单一`、`缺少前排`、`缺少持续输出`
等属于结构特征，应进入总结、优势或短板，而不是继续扩张阵容类型枚举。

枚举不是唯一战术真值。若两个标签都能由当前阵容和机制合理支持，Judge 不应仅因标签
选择不同而判错；评分应检查标签、总结与后文交互是否一致。

## 4. 关键交互

`decisive_interactions` 固定保留 3～5 条，每条包含：

- `interaction_type`：`队内协同`、`跨阵营克制` 或 `对位影响全局`；
- `actors`：参与交互的具体英雄或明确阵容单元；
- `mechanism`：发生了什么机制关系；
- `condition`：该关系成立需要什么；
- `impact`：它怎样改变阵容、团战、地图或资源判断。

核心表达链是：

```text
机制事实 → 成立条件 → 阵容级影响
```

不要求为了覆盖四条分路而凑数，也不允许只罗列技能但不说明后果。

## 5. 强势阶段与交战条件

`power_curve` 使用 `前期`、`中期`、`后期` 受控标签，并要求双方分别解释，再给出相对
比较。标签描述相对发挥窗口，不代表无条件的数值强弱。

原讨论中的“作战环境”改名为 `fight_conditions`，指交战形态、地形、视野和发起方式，
不是游戏地图类型。受控标签包括：

- 正面五人团、小规模遭遇、先手抓单、反手接团；
- 消耗拉扯、侧翼夹击、边线牵制；
- 狭窄资源区、开阔地形、推进或守塔；
- 提前占据视野、迫使对方探视野。

每方分别选择 1～4 个偏好标签、1～4 个不利标签，并解释为什么。标签只是索引，解释
必须锚定到具体英雄、机制或阵容结构。

## 6. 制胜条件

每方输出 1～3 条制胜条件，每条都必须包含：

- `goal`：希望创造什么局面；
- `execution`：阵容层面怎样执行；
- `key_condition`：成立所需的关键条件；
- `failure_risk`：最主要的失败方式。

制胜条件不能退化为适用于任意阵容的“发育、控龙、抱团”，也不提供逐波兵线、刷野
路径或装备选择。

## 7. 与历史 Baseline v1 的关系

Baseline v1 的当前可执行契约仍内嵌在 `run_baseline_eval.py`，包含 `cot_reasoning`、
简略全局分析和四个分路的双方策略。它已被多轮开发实验使用，因此保留用于历史复现，
不静默覆盖。

Schema v2 是后续正式静态阵容分析、few-shot 与 SFT 的目标输出契约。当前已经完成：

- 机器可读 JSON Schema；
- 说明性示例；
- Schema 回归测试；
- 任务范围和字段语义文档。

当前尚未完成：

- Baseline Prompt 迁移；
- `calculate_baseline_metrics.py` 从 Schema 文件加载；
- closed-book 与 fixed-KB Judge Prompt 适配；
- Evaluation Rubric 的 v2 兼容性确认；
- 使用 v2 重新运行任何模型或 API 实验。

在上述迁移完成前，旧输出不能伪装成 v2 输出，v2 也不能与历史 v1 分数直接比较。

## 8. 版本规则

- 字段增删、必填性变化或枚举语义变化必须发布新大版本或小版本，不能静默改写历史文件。
- 只修改描述文字、且不改变验证行为时，可保持 Schema 版本，但仍需记录文档日期。
- 正式实验必须保存 Schema 文件路径和 SHA-256。
